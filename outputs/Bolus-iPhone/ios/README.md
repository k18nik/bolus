# Bolus для iPhone

Настоящее приложение на SwiftUI + WKWebView, iOS 17+. Включает существующий дневник, вход в аккаунт, нативный экран Apple «Здоровье» и сохранение отчётов через системное меню «Поделиться». Оно подключается к вашему FastAPI/Next.js серверу; сервер, база и AI-ключ не упакованы внутрь телефона. Подключение OpenAI / Tokenn настраивается в профиле дневника и работает через backend.

## Установка через Xcode

1. Откройте `Bolus.xcodeproj` на Mac с Xcode.
2. В target **Bolus → Signing & Capabilities** выберите свою **Team**. При необходимости замените Bundle Identifier на уникальный. HealthKit entitlement должен поддерживаться выбранной подписью и provisioning profile.
3. Подключите iPhone, выберите его как Run Destination. При запросе iOS включите Developer Mode и подтвердите доверие Mac.
4. Нажмите **Run**. Xcode подпишет и установит приложение.
5. В Bolus укажите адрес вашего сервера и войдите в существующий аккаунт.

Для TestFlight нужны Apple Developer Program, запись приложения в App Store Connect и подписанная сборка: **Product → Archive → Distribute App → App Store Connect**. Автоматическая публикация не выполнялась. В поставке нет чужого сертификата, Apple ID или подписанной IPA.

В отдельном пакете `Bolus-iPhone.zip` также находится `UnsignedArchive/Bolus.xcarchive` — собранный arm64 Release-архив. Его можно открыть в Xcode Organizer. Он не подписан и не устанавливается непосредственно на iPhone: используйте свою Team для подписания/экспорта либо Run из проекта.

Официальная инструкция: [запуск на симуляторе и физическом устройстве](https://developer.apple.com/documentation/xcode/running-your-app-on-simulated-or-physical-devices).

## Адрес сервера

На физическом iPhone `localhost:8080` указывает на телефон. Сервер должен быть доступен телефону. Для постоянного использования настройте HTTPS-домен, `ALLOWED_ORIGIN` равным этому origin, `ENVIRONMENT=production` и `SECURE_COOKIES=true`. Пример TLS-конфигурации находится в `../nginx/https.conf.example`.

Для проверки в домашней сети подготовлен необязательный `../docker-compose.iphone.yml`. Он меняет привязку Nginx с loopback на выбранный LAN-адрес Mac и меняет разрешённый origin. Не включён автоматически. В `.env` полного проекта добавьте реальные значения:

```dotenv
IPHONE_BIND_IP=192.168.1.20
IPHONE_ORIGIN=http://Your-Mac.local:8080
```

Адреса выше — пример, их нужно заменить. Имя Mac видно в системных настройках общего доступа. Mac и iPhone должны находиться в одной сети; Docker и Mac должны работать. Затем из корня полного проекта:

```sh
docker compose -f docker-compose.yml -f docker-compose.iphone.yml up -d
```

Введите **тот же IPHONE_ORIGIN** в приложении. HTTP подходит только для локальной проверки: трафик не шифруется. Для личных данных используйте HTTPS. По возможности используйте `.local` имя: политика ATS для HTTP по числовому IP зависит от версии iOS. Глобальное разрешение произвольного HTTP в приложении не включено. В Simulator на этом Mac можно использовать `http://localhost:8080` без LAN override.

## Apple «Здоровье»

1. Войдите в дневник.
2. Нажмите сердечко в верхней панели приложения.
3. Выберите 7, 30 или 90 дней и нажмите «Разрешить чтение и подготовить данные».
4. Выберите разрешённые категории в системном диалоге Apple.
5. Проверьте сервер, аккаунт и количество записей. Нажмите «Отправить в мой дневник».

Читаются тренировки, шаги, activeEnergyBurned, appleExerciseTime и distanceWalkingRunning. Шаги и остальные дневные показатели агрегируются HealthKit по локальным дням. Нет записи данных в HealthKit, чтения инсулина, маршрутов, пульса или медицинских карт. Отказ не мешает дневнику. Отсутствие данных не трактуется как нулевая активность или подтверждённое разрешение на чтение.

Синхронизация ручная. Тренировки обновляются по UUID, сводки — по дате; повторный запрос не создаёт дублей. Недоступные при повторном чтении поля дневной сводки не затирают уже сохранённые значения. Удаления из HealthKit автоматически не переносятся. Одновременный импорт одной тренировки через XML и HealthKit может дать две записи: выбирайте один путь импорта для одного периода. XML-сводки той же даты обновляются нативной синхронизацией.

Перед отправкой сервер повторно проверяет аккаунт. Cookies ограничены выбранным origin; нативные API-запросы не следуют перенаправлениям. Веб-страницы не получают JS-мост к HealthKit. Активность попадает в дневник и аналитику, но не изменяет болюс напрямую.

[Настройка HealthKit](https://developer.apple.com/documentation/healthkit/setting-up-healthkit), [разрешения на данные](https://developer.apple.com/documentation/healthkit/authorizing-access-to-health-data).

## Проверки

Проверено в Xcode 26.1.1: Debug build для iOS Simulator и Release archive для arm64 iPhone, оба без подписи. Приложение установлено и открыто в iPhone 17 Pro Simulator (iOS 26.1); проверены адрес сервера, загрузка дневника и экран HealthKit. Три Swift-теста проверяют URL/origin и отсутствие подставленных нулей в данных. Backend-тесты проверяют идемпотентность, обновления, CSRF/аккаунт, валидацию и неизменность профиля/IOB.

Не проверено на физическом iPhone: разрешения HealthKit, реальные данные часов, подписанная установка, выгрузка файла через системное меню и работа после длительного сворачивания. Background delivery и полностью автономный нативный дневник не реализованы. Web/PWA offline queue остаётся частью веб-приложения; её работа в WKWebView требует отдельной проверки на устройстве.

```sh
swift test
xcodebuild -project Bolus.xcodeproj -scheme Bolus -sdk iphonesimulator CODE_SIGNING_ALLOWED=NO build
```
