# Детерминированные расчёты

## Единственный источник рекомендации

`app/bolus/engine.py` — чистая функция `calculate(input_snapshot, at)`. Она не импортирует HTTP, OpenAI, базу данных или frontend. Сервер загружает подтверждённую версию профиля, выбирает сегмент в IANA timezone пользователя, получает фактические введения инсулина и вычисляет IOB. Клиенту запрещено передавать ICR/ISF/target/IOB/max_bolus: Pydantic `extra=forbid`.

Версия алгоритма: **bolus-v1.1.0**. Любое изменение математики требует новой версии и повторной прогонки golden cases. Время, профиль, IOB/model id, шаг устройства, название/тип инсулина, исходные единицы и промежуточные значения сохраняются в расчёте. Исторический snapshot неизменяем; фактическое подтверждение хранится отдельным полем.

## Конкретные решения версии 1.0

1. Входная глюкоза в mg/dL делится на 18; внутренние ICR — г/ЕД, ISF — ммоль/л/ЕД.
2. `meal = carbs / ICR`.
3. `raw_correction = (glucose - target) / ISF`.
4. Положительная коррекция включена только при `glucose > correct_above`. На самом пороге — 0. Если глюкоза ниже target, отрицательная коррекция уменьшает суммарный болюс.
5. `before_iob = meal + correction`.
6. `iob_adjustment = min(iob, max(0, before_iob))`.
7. `unrounded = max(0, before_iob - iob_adjustment)`.
8. Safety Layer проверяет unrounded относительно max_bolus. При превышении — `blocked`, `recommended_bolus=null`, а не скрытое уменьшение до лимита.
9. Успешный результат округляется вниз до шага `bolus_increment` средствами Decimal: `floor(unrounded / step) * step`. Старые данные без поля сохраняют шаг 0,1 ЕД. Новые профили ручки по умолчанию используют 1 ЕД; доступны также 0,5, 0,25 и 0,1. До округления результат проверяется на max_bolus. Шаг сохраняется в snapshot и проверяется при записи фактической дозы.

Пример: 62 г / ICR 10 = 6,2 ЕД; (10,2 − 6) / ISF 2 = 2,1 ЕД; IOB 0,9 ЕД; до округления 7,4 ЕД. При шаге 1 ЕД итог 7 ЕД, при 0,5 — 7 ЕД, при 0,25 — 7,25 ЕД, при legacy 0,1 — 7,4 ЕД. Фактический ввод создаёт отдельную запись и только она влияет на следующий IOB.

Эта спецификация не утверждает, что вычитание всего IOB из еды и коррекции клинически подходит каждому человеку. Alternative IOB policies и другие модели действия должны иметь отдельные версии и клиническую проверку.

## IOB: linear-remaining-v1.0.0

Для фактически введённой быстрой дозы U, возраста t часов и сохранённой DIA D:

```
remaining(t,D) = 0                 при t < 0
remaining(t,D) = max(0,1 - t/D)   при t >= 0
IOB = sum(U_i * remaining(t_i,D_i))
```

Сразу после введения: 100%; через D/2: 50%; через D: 0%. Базальный инсулин исключён. Рекомендации без подтверждения исключены. DIA сохраняется в фактической записи, изменение настроек не переписывает старые инъекции. IOB-модель заменяется через `InsulinActionModel`.

Это **упрощённая линейная модель остатка**, не модель скорости действия и не клинически валидированная кривая препарата. Для реального применения потребуется подтверждённая стратегия, поддержка типов инсулина и проверка stacking/meal context.

## Safety Layer

Блокировки: NaN/Infinity/ненумерические входы; отсутствующая глюкоза; измерение старше 15 минут или более чем на минуту в будущем; глюкоза <3,9 или >30 ммоль/л; ICR вне (0,200], ISF вне (0,30], DIA вне [2,8], IOB вне [0,200], carbs вне [0,500], max_bolus вне (0,50], target вне [3,9,15], correct_above ниже target или выше 30, unit mismatch, невалидный результат, превышение max_bolus.

3,9 ммоль/л соответствует принятому порогу низкой глюкозы; остальные границы и время свежести — явные продуктовые ограничения прототипа, не универсальные клинические назначения. Источник по гипогликемии: [NIDDK](https://www.niddk.nih.gov/health-information/diabetes/overview/preventing-problems/low-blood-glucose-hypoglycemia).

Подтверждение разрешено только для успешного расчёта не старше 15 минут. PostgreSQL блокирует строку расчёта; уникальный client_id защищает от повторного фактического введения при retry. Максимальная фактическая доза подтверждения ограничена snapshot-лимитом. Исторический факт с большей дозой можно отдельно занести ручной записью; дневник не должен скрывать реальные введения.

## Аналитика

Среднее, медиана, min/max, population SD, CV=SD/mean*100 вычисляются Python. Диапазон [3,9;10] ммоль/л, включая границы; TBR <3,9, TAR >10. При пустой выборке показатели глюкозы — null, не ноль. Для ручных измерений используется `coverage_method=sample_based`. Сырые интервалы без наблюдений не интерполируются и не выдаются за время CGM.

Связь с тренировкой: последнее измерение в течение часа до начала, первое в течение двух часов после окончания. Это описательное сопоставление; питание, инсулин и другие confounders не исключены. Результат не формирует профиль или дозу.

## AI и персонализация

Responses API выбранного провайдера (OpenAI / Tokenn) получает агрегаты и при запросе выбранный snapshot. Structured Outputs проверяются отдельным `safety/ai_output.py`. Ни один AI endpoint не возвращает исполняемое `bolus_units`. Методов управления введением инсулина или изменения дозы у AI нет. Персонализация и изменение профиля по серии наблюдений остаются отдельным будущим модулем.
